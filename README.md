# Governed Evaluation of a Clinical Retrieval System

**BARN-AIS-EVAL-001 · v1.0** — evaluation harness, adversarial suite and release assessment for a prototype clinical RAG system.
Candidate: Javad Hezareh · Central AI Research and Safety

All data in this repository is **synthetic**. No real patient data is used anywhere.

---

## Quick start

Requires Python 3.11+ and `make`. From a clean clone:

```bash
make install     # create venv, install pinned dependencies
make validate    # schema + registry preconditions, no scoring
make eval        # full evaluation run -> results/runs/<run_id>/
make test        # unit tests
```

`make eval` is the single documented command referred to by Gate One. It requires no
arguments and no manual setup beyond `make install`.

To run without the Makefile:

```bash
python -m src.cli run --config configs/run.default.yaml
```

**Exit codes.** `make eval` exits non-zero if any case is missing a response, if any
registry precondition fails, or if any release gate fires. A zero exit means the suite
loaded completely and no gate fired — it does not by itself mean the system passed.

## What is being evaluated

The prototype receives a question, a synthetic patient context, retrieved evidence
documents with metadata, and a safety policy. It does **not** perform retrieval — its
documents are supplied as input. This has one consequence worth stating up front:
retrieval recall @ K (§4.1) characterises the test fixture rather than a retrieval
component, and a high value must not be read as evidence about retrieval quality.

### Response provenance

Every run records `response_source` in its metadata:

| Value | Meaning |
|---|---|
| `rag_prototype` | Responses generated by the system under test |
| `simulated_fixture` | Responses authored to exercise the harness |

The current responses in `results/responses/simulated_v1.jsonl` are a **simulated
fixture**. This repository therefore currently demonstrates *an evaluation harness
validated against a response fixture*, not *an evaluation of a clinical RAG system*.
Those are different claims and Gate Two makes conflating them expensive. Every reported
figure carries its `response_source`.

## Layout

```
configs/              run config, gate thresholds, severity map
data/synthetic/       synthetic patient registry
docs/                 evaluation strategy (Part One), input contract, case review
evaluation_cases/     clean + adversarial suites, distribution shifts, groundability audit
src/contracts/        the three JSON Schema contracts
src/harness/          loading, joining, orchestration — no scoring logic
src/preprocessor/     eval-side, annotate-only (parked)
src/authority/        E0–E5 state machine (Part Four)
src/scorers/          split by determinism, not by metric family
src/judge/            judge client, replayable cache, versioned prompts
src/aggregation/      rates · severity · gates
src/reliability/      evaluate-the-evaluator (block condition §3.14.5)
src/reporting/        machine-readable output, summary, evaluation card
results/              responses, confirmation events, per-run outputs
tests/                unit tests + planted-failure fixtures
```

Six layout decisions that are load-bearing rather than cosmetic:

1. **`src/scorers/` splits by determinism.** The directory listing *is* the §5 exemption
   list. Everything under `deterministic/` is exempt from the evaluate-the-evaluator
   burden; everything under `judge/` is subject to it. A metric filed in the wrong
   directory is visible in review.
2. **`aggregation/gates.py` is separate from `aggregation/rates.py`.** §3.14 is gating,
   not multiplying. Inside the aggregation math, gate logic would read as another
   weighted term.
3. **`judge/cache.py` is a reproducibility requirement.** A fixed seed does not make an
   LLM judge deterministic. Without a replayable cache, Gate One fails for every
   judge-dependent metric.
4. **`configs/thresholds.yaml` is its own file**, frozen before the first run. Assignment
   condition 4 forbids undocumented post-hoc changes; the git history of one small file
   is the audit trail.
5. **`reliability/` is top-level, not a test utility.** Instability there invalidates the
   release decision regardless of the system's scores.
6. **`tests/fixtures/planted_failures.jsonl` is the harness's own oracle.** Known
   failures live eval-side so a scorer that silently stops working fails a test rather
   than producing a clean-looking pass. No scorer reads this file.

## Reproducibility

- Dependencies pinned in `pyproject.toml`.
- Random seed set and recorded in `configs/run.default.yaml` and in every run's metadata.
- Model version, prompt version, evaluation version, preprocessor version,
  `response_source`, seed, date and `run_id` are recorded **before** any scorer executes,
  so a run remains attributable even if it later fails.
- Judge calls go through a content-addressed cache committed with the run, so
  judge-dependent metrics replay offline and reproduce exactly.
- No API keys in the repository. The judge reads `ANTHROPIC_API_KEY` from the
  environment; `make eval` runs fully offline against a committed judge cache.
